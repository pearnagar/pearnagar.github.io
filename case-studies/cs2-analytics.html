CS2 Analytics Engine

A compact production-style analytics platform that turns Steam market data into a scheduled data pipeline, API, browser dashboard and observable Kubernetes workload — packaged as one Helm release.

Architecture

The design separates ingestion, persistence, serving and observability while keeping the developer experience simple enough to run locally on Minikube.

The engineering problem

The interesting part was not scraping a price endpoint. It was turning that simple task into a small system with deployment boundaries, health signals, secrets, ingress, persistence and repeatable delivery.

01 · INGESTION

Scheduled, not always-on

The scraper runs as a Kubernetes CronJob every ten minutes. That keeps the workload aligned with the task: short-lived collection jobs rather than a permanently running process.

02 · PERSISTENCE

State is explicit

Market samples are stored in PostgreSQL as time-series rows. The database is deployed as a StatefulSet so persistence is treated differently from stateless services.

03 · API BOUNDARY

The browser never needs the API key

The nginx frontend reverse-proxies /api/* to FastAPI. That gives the browser a same-origin path and avoids exposing the API credential to frontend JavaScript.

04 · OPERABILITY

Health and metrics are first-class

The API exposes health, readiness and Prometheus metrics endpoints. Grafana sits on top of Prometheus so system behavior can be inspected instead of inferred.

Key decisions

These are the choices that make the project read like infrastructure engineering rather than a collection of disconnected containers.

One Helm release

The API, scraper, frontend and application-side Kubernetes resources are templated under one chart, giving the stack one repeatable installation path.

Real ingress names locally

sslip.io hostnames encode the Minikube IP, removing the need for manual hosts-file edits while still exercising ingress routing.

Security in the container baseline

Containers run non-root and use read-only root filesystems where feasible. CI also includes image scanning with Trivy before an image is considered releasable.

Delivery & failure signals

The project deliberately includes the boring parts that become important the first time a deployment or dependency fails.

CI checks

  • Dockerfile linting with Hadolint
  • Helm linting
  • Container builds per service
  • Trivy vulnerability scans

Runtime signals

  • /healthz and /readyz
  • /metrics for Prometheus
  • Grafana visualization
  • Ingress endpoints for the app and monitoring surfaces

What I would improve next

A case study is more useful when it also shows where the current design stops.

Secrets

Move deployment secrets from runtime overrides toward Sealed Secrets or an external secret manager so encrypted configuration can safely participate in GitOps.

TLS & deployment automation

Replace the local self-signed certificate with a trusted local flow and turn the currently disabled deployment stage into a tested promotion path.
