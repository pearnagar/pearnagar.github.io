Autonomous SRE Agent

A production-style incident investigation and remediation agent built with Python, LangGraph and Claude. It receives an alert, decides which operational tools to use, loops through evidence gathering and returns a root-cause analysis with any bounded remediation it performed.

Architecture

The design separates alert intake, agent reasoning and operational tools. The LLM chooses actions through LangGraph until it reaches a final answer or the safety cap terminates the loop.

The engineering problem

Operational automation is useful only when the system can gather evidence, choose the right action and remain constrained when the model behaves unexpectedly.

01 · INVESTIGATION

Evidence before action

The agent can query recent Loki logs instead of reasoning from the alert title alone, giving the model live operational context before it proposes or performs remediation.

02 · TOOL USE

No fixed runbook

Claude is bound to explicit operational tools and decides which tool to invoke based on the evolving incident state rather than a hardcoded sequence.

03 · REMEDIATION

Reasoning connected to action

The tool layer can restart a Docker container or replay a signed Stripe webhook, demonstrating how an agent can move from diagnosis to controlled operational action.

04 · SAFETY

Autonomy needs limits

A custom router terminates the decision/tool cycle when the retry count reaches the configured maximum, preventing unbounded loops and limiting worst-case latency and cost.

Key decisions

The project treats the agent as part of an operational system rather than as a chat interface.

Stateful graph instead of a single prompt

LangGraph maintains incident state across decision and tool-execution nodes, allowing investigation to evolve as new evidence appears.

Explicit tools with narrow responsibilities

Each operational capability is exposed as a focused tool: fetch logs, restart a container or replay a webhook. That makes the agent's available actions inspectable and testable.

Fail closed at the API boundary

If graph execution fails because of an LLM, tool or timeout error, the webhook endpoint returns an explicit 500 response instead of hiding the failure or crashing the service.

Validation

The repository includes sanity checks for the full agent graph and for standalone operational tools, so tool behavior can be tested independently of the LLM loop.

Agent path

An end-to-end graph test sends a mock incident through the agent loop and verifies that the graph can reach a final analysis.

Tool path

Standalone tests exercise Docker connectivity and webhook simulation without requiring the model to make the decision.

What I would improve next

The current project proves the agent loop and operational integrations locally. The next iteration would focus on production-grade approval and evaluation controls.

Human approval for risky actions

Split tools into read-only and mutating classes, then require explicit approval before state-changing operations while allowing evidence gathering to remain autonomous.

Evaluation and audit trail

Persist tool calls, evidence, model decisions and remediation outcomes, then evaluate incident-resolution quality against a repeatable test set before expanding permissions.
