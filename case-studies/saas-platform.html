Acme SaaS Platform

A production-style SaaS monorepo that treats authentication, billing, data consistency and observability as part of the product architecture instead of afterthoughts.

Architecture

The application is deliberately simple at the boundary — one Next.js app — but explicit about the backend concerns that matter: auth, transactional billing updates, database access and operational telemetry.

The engineering problem

A SaaS starter is easy to make look functional. The harder part is making the state transitions around authentication and billing deterministic, observable and safe to retry.

01 · WEBHOOK TRUST

Verify before mutating

Stripe webhook signatures are checked against the raw request body before any billing state is accepted. Tampered simulator events are expected to fail with HTTP 400.

02 · IDEMPOTENCY

Retries must be boring

Incoming event IDs are persisted and deduplicated. Re-delivery of the same event does not repeat a subscription mutation.

03 · CONSISTENCY

Tier and subscription move together

Webhook processing updates the relevant user tier and subscription records within a transaction so the dashboard does not observe half-completed billing state.

04 · TELEMETRY

Every important mutation leaves a signal

API routes, webhooks and mutating server actions emit structured JSON with timestamp, level, event and request ID, while explicitly excluding secrets.

Key decisions

The project emphasizes contracts: a contract for database access, a contract for logging, and a contract for handling external events.

Database access through Drizzle

The schema, client, migrations and seed data live in a dedicated package, keeping persistence concerns explicit and reusable across the monorepo.

Offline webhook simulation

A local simulator signs payloads using the same HMAC model as Stripe. That makes success, downgrade and tamper scenarios testable without depending on a live Stripe listener.

Observability as a package

Structured logging is centralized so event names and request context are consistent rather than reimplemented independently in each route.

Operational view

The local observability path is intentionally complete enough to answer practical questions during a billing incident.

What can be queried

  • Processed webhook events
  • Authentication events
  • Error-level application events
  • Context grouped by event name and level

What the rules protect

  • No secrets in logs
  • Strict TypeScript
  • Verified webhook signatures
  • Idempotent external event handling

What I would improve next

The current stack is intentionally local-first. The next step would be turning the same contracts into production deployment guarantees.

Async billing pipeline

Introduce a durable queue between webhook acceptance and downstream processing so spikes and transient failures can be absorbed without coupling acknowledgement latency to business logic.

SLOs, tracing and managed observability

Add distributed traces, explicit latency/error SLOs and a managed log/metrics backend for a deployed environment, then validate those signals with failure injection.
